# ADR-0053: Web Push from the gateway, fed by Alertmanager, to the installed PWA

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decision register:** D71 (implements D13's Web Push half; Pushover emergency stays the critical path, D45)
- **Related:** SE-060..SE-063, UI-044, MN-003, [ADR-0012](0012-web-ui-spa-sse-pwa.md), [ADR-0027](0027-monitoring-ops-slice.md), section 14 prompt (PWA), section 13 prompt (alert channels), research 07 §4

## Context

D13: an installed PWA with Web Push, plus Pushover emergency priority for critical alerts. Phase 2 made Alertmanager the only router (D45) and delivers Pushover. Web Push needs: VAPID keys (RFC 8292), message encryption (RFC 8291, aes128gcm), subscription storage, and a sender reachable by alert routing. iOS delivers Web Push only to Home Screen web apps (16.4+); Safari 18.4+ supports Declarative Web Push (no service worker needed). Section 13 requires alerts to avoid sensitive values on lock screens (configurable), and alerting must not depend on the UI (Pushover covers that).

## Decision

- **The gateway sends Web Push.** It owns the owner's subscriptions (auth data) and holds the VAPID key (`webpush_vapid_key`, P-256 PEM generated by `make secrets`). Encryption and VAPID are implemented with the Go standard library in `services/api-gateway/internal/webpush` and pinned to the RFC 8291 Appendix A test vector.
- **Alertmanager feeds it.** Every notifying receiver (warning, critical, report) gains a `webhook_configs` entry to `http://api-gateway:8082/internal/alertmanager/webhook` with a bearer token from `alertmanager_webhook_token`. The internal listener (`TB_INTERNAL_HTTP_ADDR`, `:8082`) is on the backend network only, never published or tunnelled. Routing, grouping, quiet hours (warnings muted 22:00–07:00 New York; critical never), and repeats stay Alertmanager's, so Web Push and Pushover follow the same rules.
- **Messages.** One notification per alert group: `[SEVERITY] alertname`, summaries (at most three lines), a stable tag and RFC 8030 Topic per group (newer states replace older undelivered ones), `Urgency: high` and require-interaction for critical, TTL 1 h critical / 4 h otherwise, in the Declarative Web Push shape (`{"web_push": 8030, "notification": …}`) so Safari can show it without the worker. `TB_PUSH_REDACT` (default on) keeps summaries off lock screens: severity and alert name only. Fills are pushed only while `alerts.push_fills_enabled` is on.
- **Subscriptions.** Stored in `auth.push_subscriptions` with endpoint and keys AES-256-GCM sealed under a gateway-derived key (the endpoint is a capability); only the push host and a SHA-256 prefix are in clear. Endpoints must be https on an allowlisted push service (FCM, Mozilla, Apple, Windows; `TB_PUSH_ALLOWED_HOSTS`), so a subscription cannot turn the gateway into an SSRF proxy. 404/410 deletes the subscription; other failures are recorded without the endpoint. Subscribe and unsubscribe are audited.
- **PWA.** PNG icons (192, 512, maskable 512, 180 Apple touch, 96 badge) rendered from the SVG mark; a manifest with `id`, shortcuts, and theme; `public/sw.js` only shows notifications and focuses or opens the app on click (same-origin paths only). It caches nothing and intercepts no request, so a stale bundle can never keep running. The Notifications page handles install (Chromium prompt, iOS instructions), enabling push per device, the device list, and a test push.

## Alternatives considered

| Option | Why not |
|---|---|
| Web Push from the monitor service | The monitor would need the owner's subscriptions (auth data) and a second copy of the VAPID key; the gateway already serves the PWA and owns auth |
| Gateway subscribes to `alert.>` on the bus | Misses Prometheus-rule alerts (service down, feed stale) that reach only Alertmanager; would duplicate grouping and quiet hours |
| `webpush-go` or another library | Small, but a new dependency on the critical alert path; the protocol is short and pinned to the RFC test vector here |
| ntfy / Telegram | A tailnet-only ntfy does not reach iOS promptly; Telegram is optional per research 07 §4 and not needed with Pushover |
| A caching service worker (offline shell) | A trading UI must not run stale code; every page needs a live session anyway |

## Consequences

- Positive: the installed app gets warnings, critical alerts, reports, and optionally fills, following the same routing as Pushover; no new service.
- Negative / risks: Web Push depends on the gateway and the browser vendors' push services; critical alerts therefore keep Pushover emergency priority as the primary path (D13). Existing installs need `make secrets` (new VAPID key, webhook token) and a restart of api-gateway and Alertmanager.
- Follow-up: section 13's alerts inbox can deep-link notifications (the payload's path) once its route exists.

## Validation

`TestSE060RFC8291TestVector`, `TestSE060VAPIDHeaderIsAValidES256Token`, `TestSE060SendRoundTripAndGoneMapping`, `TestSE061EndpointAllowlistBlocksSSRF`, `TestSE061PushSubscriptionsAreValidatedSealedAndAudited`, `TestSE063AlertmanagerWebhookDeliversToEveryDevice`, `TestSE062RedactedNotificationsCarryNoSummary`; on a phone: install the PWA, enable push, `Send a test`, and a critical test alert arrives as both Web Push and Pushover emergency (Gate 5; owner action).
